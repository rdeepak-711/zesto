How should the unified FSM work?

Three ways to make one FSM serve salons, bakeries, photo studios, and more

A

Business-type switch inside states

Minimal change. Add if businessType === 'salon' branches in existing states.

AWAITING_NAME:
  if bakery → go to AWAITING_ADDRESS
  if salon → go to AWAITING_DATE
  if photo_studio → go to ENQUIRY_FLOW

Pros

  • Simple to add
  • One file

Cons

  • Gets messy fast
  • 4th type = spaghetti
B

Capability flags (Recommended)

Tenant has flags: hasBooking, hasEnquiry, hasDelivery. FSM reads flags, not type name. Adding a new type = just set the right flags, no code changes.

Salon: hasBooking=true, hasCart=true
Bakery: hasDelivery=true, hasCart=true
Photo: hasEnquiry=true, hasCart=false
Spa: hasBooking=true, hasCart=false

Pros

  • No new code per type
  • Mix capabilities freely
  • Future-proof

Cons

  • More upfront DB change
  • Flag combos need testing
C

Extension modules

Core FSM handles greeting/cart/payment. Extensions register extra states. booking-extension.ts, enquiry-extension.ts each export states that slot in.

core-fsm.ts → base states
+ booking-ext.ts → AWAITING_DATE/TIME/AGE
+ enquiry-ext.ts → ENQUIRY_* states
composer.ts → merges by capability

Pros

  • Clean separation
  • Each ext testable alone

Cons

  • More files to build
  • Merging state machines is tricky

My recommendation: B (Capability flags) — it gives you the most flexibility without complexity. A new business type is just a row in the DB with the right flags set. No code deployment needed to support a new variant of salon or bakery. The FSM branches on tenant.capabilities instead of a type string.
